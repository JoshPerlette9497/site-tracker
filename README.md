# Site Log — Handoff Notes for Claude Code

This is a construction site management PWA for Josh Perlette (site superintendent at Slokker Homes), currently a single-file HTML app. It needs to be restructured into a proper multi-file project, put in git, pushed to GitHub, and connected to Netlify for auto-deploy.

## What this app does
- **Today / Brief**: daily priorities, due/overdue deficiencies and checklist items
- **Units**: per-unit "Rounds" — current phase, current/next trade, risk level (auto-computed from days since last walk), round history
- **Phase Checklist**: 32 checklist groups (191 items total) matching Slokker's construction phases, each with a computed due date, collapsible checkbox list, and completion count (e.g. "6/10")
- **Deficiencies**: location-based (unit or site-wide), due dates, owner (Trade/Josh/Unassigned), push/backlog tracking
- **Schedule**: Buildertrend schedule data (manually synced — Buildertrend has no API, so this is pasted in from Outlook calendar data periodically)
- **Log**: daily log, auto-generated from activity + historical entries migrated from Notion
- **Sync**: schedule import, deficiency import, backup/restore (full JSON export/import)

## Data / Storage
Currently backed by Supabase (already set up):
- Project URL: `https://iafzmkwahiusfdxodgdi.supabase.co`
- Single table `app_data (key text primary key, value text, updated_at timestamptz)` — a simple key-value store. The app reads/writes JSON blobs by key (`units`, `defs`, `schedule`, `checklistGroups`, `groupInstances`, `roundHistory`, `logHistory`, `master`, `instances`, `lastBackup`).
- RLS policy on `app_data` requires every request to carry an `x-site-key` header matching a shared passphrase (see "Access code" below) — replaced the old wide-open anon policy once the site moved to a public GitHub Pages URL.
- The anon key is in `js/storage.js` under `SUPABASE_ANON_KEY` — safe to keep client-side (that's how Supabase's anon key is designed to work); the RLS policy above is what actually gates read/write access now.

### Unified task model — Phase 1 (deficiencies only)
`defs` items now carry a shared task shape, added in `js/data.js` (`migrateDefTaskFields_v1`, `unifiedTaskStatus`): `verifier`, `followUpDate` (distinct from `dueDate` — a check-back reminder, not a deadline), `startedAt`, and an append-only `notes[]` log (seeded from any existing `pushReason` on migration, which itself is untouched and still drives the push/backlog UI). `unifiedTaskStatus(d)` is computed on read, never stored, so it can't desync from `owner`/`status` edited through the existing Add/Edit Deficiency modals.

Deliberately **not** touched: phase checklist groups/items (`checklistGroups`/`groupInstances`) and the legacy `master`/`instances` pair. They stay their own thing — surfaced by `currentPhaseChecklistGroup()`/`buildSuggestedPlan()` off round-logging (`currentPhase`/`lastWalkDate`), which this phase leaves completely alone.

### Phase 2 — NOW section
`buildSuggestedPlan()`'s tiebreak order is now due date → category → priority → shortest `estimatedMinutes` (previously fell back to array order past priority). The **Today tab was deleted** — Brief is now the sole/default tab (`activeTab` defaults to `'brief'`; `renderToday`/`cardForInstance` removed). Brief opens with a **Now** section (`nowSection()` in `js/render.js`): a pinned, visually distinct (`.now-card`) preview of the Suggested Plan queue's own first item — not a separate selection, so reordering the queue via drag moves Now with it. Falls back to the earliest open item whose new `followUpDate` has arrived (`followUpsDue()` in `js/data.js`) when the queue is empty — the first real consumer of that Phase 1 field. No conflict/time-of-day detection (nothing in the model has a time component) — scheduling around fixed commitments stays manual.

**Closing the loop on the Phase 1 fields:** the Edit Deficiency modal now has Verifier and Follow-up Date inputs, plus an append-only Notes log (add-only from the UI — existing notes aren't editable, matching the field's design). Every open deficiency card also gets a **Start** button (hidden once `startedAt` is set) so `startedAt` has a real trigger instead of being unreachable. Verified end-to-end in a headless browser: notes append correctly, verifier/follow-up persist through the existing overbook-warning double-confirm flow, Start sets `startedAt` and removes itself from the card.

### Phase 3 — Capacity planning
A **Capacity** section on Brief (`capacitySection()`/`buildCapacityForecast()`) projects Josh's own (`MY_ACTION`-equivalent, owner-`Josh`) open workload against `dailyAllowanceMinutes` across the **next 5 business days** (`businessDaysForward()`/`nextBusinessDay()` in `js/data.js` — Mon–Fri only, weekend due dates roll forward onto the next business day rather than silently dropping out of the forecast). Uses the same greedy fill and tiebreak as `buildSuggestedPlan()`; whatever doesn't fit a day cascades into the next day as a push suggestion. Confirming a suggestion (**Push** button) moves the item's real `dueDate` forward one business day and records it via `pushCount`/`pushReason` — the same backlog-push semantics a checklist instance's Push button already tracked, but deficiencies had the fields with no UI writing to them until now. **Keep** dismisses a suggestion for the current render only (no data change — it'll resurface next time if the underlying due-date pile-up is still there). Trade/Delegated items are excluded entirely, same as `buildSuggestedPlan()` already excludes them. Verified in an isolated Node harness (weekend rollover, cascade behavior, push confirmation) and a headless browser against real deficiency data with a deliberately tiny budget to force overflow.

### Phase 4 — Subtask breakdown (no AI)
Originally scoped as an "AI prioritizer," but the app has no backend and no LLM API key can safely live in client JS (unlike the Supabase anon key, which is safe only because of its RLS policy) — so this shipped as a plain rule-based prompt instead, no model call involved. Saving a deficiency (Add or Edit) whose estimate crosses 60 minutes triggers `openSubtaskPromptModal()`: Josh names and sizes as many subtasks as he wants on the spot. Confirming (`splitDefIntoSubtasks()` in `js/data.js`) creates each subtask as a **full standalone deficiency** (own owner/due date/status/etc., tagged with `parentId` for provenance only — nothing reads it yet) rather than a lightweight sub-item, so subtasks work with Suggested Plan, capacity planning, and follow-ups with zero special-casing. The parent is marked `Done` with no `completedDate` (it wasn't completed, it was decomposed) and gets a note recording what it was split into — reuses the existing `status!=='Done'` filter everywhere instead of threading a new status value through every query. Declining ("Not Now") sets `subtaskPromptDismissed` so it's a one-shot ask, not a nag on every future edit. Verified in a headless browser: prompt fires on crossing the threshold from both Add and Edit, subtasks persist correctly, decline suppresses re-prompting on a later re-save.

### Phase 5 — Capture button

Brief also gets a **Needs triage** line (next to the existing Backlog line) linking straight to that filtered view, so nothing requires remembering to go look. Verified in a headless browser: FAB persists across tab switches, a captured item lands with the right (empty) fields, and the triage link correctly navigates and shows it.

### Fixed vs. flexible due dates — auto-scheduling
Before building, an audit found this request's premise ("task-prioritizer system," "fixed_commitments," a priority-tier scheme with a "near-due checklist items" tier, "longest duration" tiebreak) didn't match anything in the actual codebase — flagged to Josh, who confirmed the resolution before any code was written:
- Tiebreak stays **shortest** duration first (the existing, already-tested Suggested Plan/Capacity behavior), not longest.
- Scope is **deficiencies only** — checklist items stay untouched, preserving the boundary set earlier this session.
- The auto-scheduling window is **capped at the existing 5 business days** (`businessDaysForward`), not dynamic per task.

**What was built:** `defs` gain `dueType` (`'fixed'`|`'flexible'`, migrated/defaulted to `'fixed'` everywhere — zero behavior change for anything not explicitly opted in) via `migrateDefDueType_v1()`. `computeWeekSchedule()` (`js/data.js`) is the new single source of truth, replacing the internals of `buildCapacityForecast()`: **fixed** items keep the exact pre-existing cascade-from-due-date behavior (unchanged code path); **flexible** items are placed by earliest-deadline-first, first-fit-from-today — processed in due-date-ascending order (least slack gets first pick of capacity), each one taking the earliest day in `[today, min(dueDate, 5th business day)]` with room, forced onto the day nearest its deadline if nothing in the window fits. `buildSuggestedPlan()` (today's queue — Now/Suggested Plan) and `buildCapacityForecast()` (the week view) both now derive from the same `computeWeekSchedule()` call, so a flexible item placed "today" can never disagree between the two views.

**Judgment calls, for review:**
- `scheduledDate` is **computed on read, never stored** — deviates from the literal "add a field" ask, but matches the established pattern in this file (`unifiedTaskStatus`, `dueStatus`, `computeRisk`) and gets Josh's "re-enters the pool fresh, re-evaluated alongside everything else" rescheduling requirement for free, with zero roll-forward code needed.
- "Escalate within 2 days of due_date" needed **no special-case code** — due-date-ascending processing plus a shrinking placement window already pushes an approaching-deadline flexible item toward the front of the queue and the start of its own window as time passes. Worth double-checking this actually reads as "escalated" to Josh in practice, since there's no explicit tier promotion happening.
- The overbook double-confirm warning (Add/Edit modals) now **only fires for fixed dates** — it exists to stop cramming too many hard-anchored items onto one day, which doesn't apply to something the scheduler is already spreading out automatically.
- **Worth flagging directly**: earliest-fit-from-today means a flexible item due a week out can still land on *today* if there's room, purely because nothing claimed that slot first — not spread evenly across its window. Confirmed as correct against the literal spec ("prefer a day or more before deadline") in a dedicated test case, but if the felt experience should instead lean toward *closer to today without cramming it in immediately*, that's a different algorithm and worth raising.

Verified with a 7-case Node harness (fixed-only regression against the pre-existing algorithm, front-loading with open capacity, flexible correctly skipping a nearly-full fixed day, urgent-vs-relaxed flexible competing for the same day, forced placement when a whole window is full, Suggested-Plan/Capacity consistency, weekend due-date rollover) and a headless browser against both synthetic and the real 230-deficiency dataset (all defaulting to fixed with zero regression, then a mixed scenario with no errors). Add/Edit modals gained a Schedule (Fixed date / Flexible) select; display is identical either way per spec — nothing in `cardForDef` changed.

### Subtask due-date spread
Audit found the original subtask feature gave every subtask the **same due date as the parent** (no spreading) and the breakdown modal collected no date at all — so Josh's "break a task into one piece per day" workflow required manually editing each subtask's date afterward, and even then a `flexible` subtask could let the auto-scheduler re-clump them the moment a day had spare capacity, undoing a deliberate spread.

Each subtask row in the breakdown modal now has an optional due-date field. `suggestSubtaskDueDates()` (`js/data.js`) fills in whatever's left blank — evenly spread across the business days from today through the parent's real due date (`businessDaysUntil()`, new alongside `businessDaysForward()`), first subtask landing today, last landing on the due date itself. Any date Josh sets by hand is kept as-is; blanks are filled independently by index position in the full spread, not gap-filled around the manual ones — simpler, but means a manual date can occasionally land on the same day as an auto-filled one (verified, not a bug — flagged here as a known simplification). Every subtask from this flow is **always `dueType:'fixed'`**, regardless of what the parent was — deliberate placement, not something the scheduler should be free to optimize away.

Verified with a dedicated Node harness (exact N-days-equals-N-subtasks case with no repeats, uneven spreads, weekend due-date rollover, no-due-date fallback, more subtasks than available days degrading gracefully instead of erroring, manual dates respected alongside auto-filled ones) and a headless browser: 4 subtasks with blank dates landed on 4 distinct business days, all fixed, no errors.

### Subtask usability fixes
Three real bugs/gaps found by reproducing each in a headless browser (not assumed):

1. **The subtask text field was ~22px wide, unusable.** `subtaskRowHtml()`'s three fields (free-text, minutes select, date input) sat in one flex row; the two short fields had no explicit `flex`, so the global `input,select,textarea{width:100%}` rule became their flex-basis and squeezed the free-text field (`flex:1`, flex-basis 0) down to almost nothing — confirmed with a screenshot and computed `getBoundingClientRect()` (22px before, 358px after). Fixed by stacking: the text field gets its own full-width line, the minutes/date pair sits below in their own row — the same pattern every other multi-field group in this app already uses, instead of patching the 3-way flex fight.
2. **Created subtasks were invisible** — `splitDefIntoSubtasks()` was working correctly (verified: subtask and `parentId` both persisted), but nothing surfaced them: they could land in "No Date" while Josh was looking at the default "Due Date" tab, and the parent (always marked Done, always on the Done tab) showed no trace of having been split — that information only existed in its Notes, unread. Fixed two ways: `subtaskLineageTag()` adds a small `· ↳ part of: <parent>` or `· split into N subtasks` fragment to both `defRowWithActions()` and `defRowDone()`'s item-meta line, visible on the row itself in any tab; and `openSubtaskPromptModal()`'s save handler now always jumps to the Deficiencies tab (filtered to "Due Date" or "No Date" depending on whether the new subtasks got dates) right after creating them, regardless of where the modal was opened from.
3. **No way to break down an existing item after the fact.** The only trigger was the automatic >=30-minute prompt at Add/Edit save — an item created before this feature existed, or one already dismissed once (`subtaskPromptDismissed`), had no path back in. Added a "Break Into Subtasks" button to the Edit Deficiency modal (hidden once the item is Done) that opens the same `openSubtaskPromptModal()` directly, bypassing the estimate/dismissed gates entirely since this is an explicit manual request.

Verified in a headless browser: text field width before/after, full create→navigate→tag flow end-to-end (parent shows "split into 2 subtasks", subtask shows "part of: ..."), and the manual button working on a 15-minute already-dismissed item while correctly staying hidden on a Done one.

Verified in a headless browser: seeded a Done parent with two subtasks, opened the parent's Edit modal and confirmed both subtask rows render with their due dates and no stray "part of" link (the parent has no `parentId`); clicked a subtask row and confirmed it navigated to that subtask's own modal, which showed the "part of" link with the parent's description; clicked that link and confirmed it navigated back to the parent's modal with its two subtask rows still intact.

### Button press feedback + duplicate-tap guard
Josh reported: taps felt "stagnant" with no visible sign anything had registered, which led to tapping Add/Save multiple times and ending up with duplicate entries. Root cause: `*{-webkit-tap-highlight-color:transparent;}` (near the top of `style.css`) strips iOS Safari's native tap flash so it doesn't clash with the app's own colors, but nothing was added in its place — so on a real phone, a tap gave zero visual feedback, and a save handler that has to await a Supabase write before closing its modal made that gap in feedback last long enough to invite a second, third tap.

Fixed two ways, addressing both the feeling and the actual consequence:
1. **Visible press feedback.** `style.css` now gives `.btn`, `.capture-fab`, `nav.tabs button`, and every clickable row (any `.card` with inline `cursor:pointer` — covers `.def2-card` and friends without needing to enumerate every specific class) an `:active` state: a quick scale-down + darken/brightness shift on a fast (0.08s) transition, so a tap visibly "presses" the instant it lands, independent of how long the actual save takes.
2. **A real double-submit guard, not just cosmetic.** A single capturing-phase `click` listener in `js/app.js` disables whichever `<button>` was just clicked and re-enables it ~500ms later — done once, globally, rather than touching each of the ~25 individual save/add handlers across this codebase. This relies on a real (and verified) browser behavior: setting `disabled = true` on an element *during* the capture phase of its own click does not cancel that same click's dispatch — the button's own handler still runs to completion — it only blocks a *second*, rapid click on that same button from doing anything. A deliberate second click after the 500ms window (e.g. confirming an overbook warning — "Save Anyway") still works normally.

Verified in a headless browser: confirmed the `:active` transform actually applies (had to root-cause two false test failures first — `Element.matches(':active')` doesn't reliably reflect CDP-synthetic mouse presses in this environment even though the style itself is correctly applied, and a blocked-network "couldn't save" toast can transiently sit on top of the element being tested — neither was a real bug, both were headless-test artifacts, caught by checking `document.elementFromPoint()` and computed style directly instead of trusting `.matches()`); a rapid double-click on "+ Add Subtask" added exactly one row, not two, and the button re-enabled and worked again after the debounce window; and the existing overbook-confirm flow (click "Add Deficiency" → warning appears → click "Add Anyway") still saves correctly when the second click comes after the window, so the guard doesn't interfere with intentional same-button double-clicks.

## QC Phase Check + Controlled Checklist Evolution
A full feature request: repeatable QC audits of an existing phase checklist (Pass/Issue/N/A per item), a place to record things noticed that aren't on the checklist ("Discovered Items") without those automatically becoming checklist items, and a deliberate review step where each discovery gets decided NEW / MERGED / REJECTED before it can ever change the checklist. Built entirely on top of the existing Phase Checklist system (`state.checklistGroups` + `state.groupInstances`, surfaced inside `openUnitDetail()`) rather than a new tab or a parallel data model — researched that architecture first (data model, persistence pattern, photo upload, modal/render conventions) before writing anything, since the goal was to extend what's there, not bolt on something separate.

**Two new top-level data structures**, both wired into `loadAll()` the same way every other `state.*` key is (`sget('checklistVersions', [])` / `sget('qcInspections', [])` — no schema migration needed, the whole backend is one schemaless key-value table):

- **`state.checklistVersions`** — an append-only log, one entry per time a checklist group's items actually change: `{id, groupId, versionNumber, createdDate, items (full snapshot), reason, originatingInspectionId}`. Never edited or deleted, only appended to — this is "why did the checklist change" history.
- **`state.qcInspections`** — one record per QC check run: `{id, unitId, groupId, phaseName, checklistVersionNumber, checklistSnapshot (frozen copy of the items at start time), startedAt, completedAt, itemResults ({itemId: 'pass'|'issue'|'na'}), itemNotes, discoveries[], status:'in_progress'|'completed'}`. Each discovery: `{id, description, photos[], notes, severity, decision: null|'NEW'|'MERGED'|'REJECTED', mergedIntoItemId, createdItemId, reviewedAt, createdAt}`.

Each `checklistGroups` entry also gets a `version` number now (a one-time migration, `migrateChecklistGroupVersions_v1()`, backfills `version:1` plus a matching v1 snapshot in `checklistVersions` for every group that predates this feature, following the exact same gated-migration pattern — `sget('migrated_..._v1', false)` — every other schema change in this codebase already uses).

**Deliberately left untouched:** the existing boolean `itemStatus` checkbox tracking on `groupInstances` (ongoing, perpetual completion tracking across a unit's whole lifecycle) is a different concept from a QC check (an episodic, start-to-finish audit event) and the two now coexist on the same expanded group card — Pass/Issue/N/A buttons for the QC system, the original checkboxes below them under their own "Ongoing completion tracking" label — rather than repurposing or merging the two, since conflating "is this done" with "did this pass QC" would have broken the existing tracking Josh already relies on.

**The workflow, start to finish** (`js/render.js`):
1. **Start** — every expanded phase-checklist group card (`renderPhaseGroupRow()`) now has a "Start QC Check" button (becomes "Continue QC Check" + a "QC In Progress" badge if one's already open for that unit+group — `qcInspectionInProgress()` guards against ever starting a second one). `startQcInspection()` freezes the group's current `version` number and a deep copy of its `items` onto the new inspection record — later checklist edits, from this same inspection's own review or any other, can never retroactively change what an already-run inspection shows it was checked against.
2. **Run the checklist** (`openQcCheckModal()`) — every item from the frozen snapshot gets a Pass / Issue / N/A button row; picking Issue reveals an optional note field. None of this touches the live checklist.
3. **Record discoveries** — a lightweight "+ Add Discovered Item" form (description, optional severity Low/Medium/High, optional notes, optional photos via the exact same `uploadSafetyPhoto()` bucket/upload path the Safety Walkthrough feature already uses — verified structurally in a headless browser: same `hazard-photos` bucket, same hidden-input-triggered-by-visible-button pattern, same multi-file sequential upload-with-progress-label). A discovery's `decision` stays `null` until it's explicitly reviewed — nothing here can change the checklist yet.
4. **Finish** — if there are zero discoveries, the inspection completes immediately. If there are any, "Finish QC Check" instead opens the review screen (`openQcReviewModal()`): each discovery shows its description/severity/notes, a plain-language "why it matters" hint (scaled to its severity), up to 3 "possibly already covered by" existing items (a non-AI keyword-overlap match against the group's current items, `relatedChecklistItems()` — purely a hint to speed up a MERGE decision, never an automatic one), and the four-question reminder from the request verbatim ("is this high consequence, reasonably likely to recur, worth actively checking for every time, and not already covered?"). Three decision buttons per discovery, defaulting to **Don't Add**: picking **Merge** reveals a dropdown of the group's current items (defaulting its wording box to that item's current text, editable) and picking **Add New** reveals a required wording box plus a section/subgroup picker. Confirming requires wording for every NEW/MERGED choice.
5. **Apply decisions** (`finishQcInspection()`) — REJECTED touches nothing (the discovery stays on the inspection record as history only). MERGED overwrites the target item's `text` in the live `checklistGroups` and records `mergedIntoItemId`. NEW appends a brand-new item and records `createdItemId`. If (and only if) at least one NEW/MERGED happened, the group's `version` bumps by exactly 1 and a single new `checklistVersions` entry is appended with a `reason` string built from whatever changed — so three discoveries that are all REJECTED produce zero version bumps, and three that all change the checklist in the same finish still only produce one new version, not three.
6. **Next inspection picks it up automatically** — `startQcInspection()` always reads the group's *current* `version`/`items`, so the very next QC check (same unit or a different building entirely) snapshots whatever the checklist now looks like, with zero extra steps.
7. **History** — a "QC History" button on every group card (`openQcHistoryModal()`) lists every `checklistVersions` entry for that group (version number, date, reason) and every completed inspection at that specific unit (pass/issue/n/a counts, discovery count); tapping an inspection opens a read-only `openQcInspectionDetailModal()` showing its full frozen checklist-at-the-time with each item's result/note and each discovery's final decision — the exact record of what was checked and why the checklist did or didn't change, untouched by anything that happened since.

**Why this can't become an ever-growing issue database:** a discovery has exactly three possible resting states (NEW/MERGED/REJECTED) and no fourth "just sitting there" state — the review screen requires every discovery to be explicitly decided before the inspection can finish, the checklist itself is never touched automatically, and REJECTED (the pre-selected default) costs nothing — no version bump, no new item, just a preserved record of what was seen.

Verified in a headless browser across two inspection cycles on the same unit+group: (1) start → mark Pass/Issue+note/N/A → add a discovery → "Save & Back to Unit" (confirms it stays `in_progress`, shows the "QC In Progress" badge and "Continue QC Check" label, and resuming shows the earlier discovery still there) → Finish → review screen appears (since a discovery exists) → decide **NEW** with wording → confirm → checklist version bumped 1→2, new item appended with the exact wording, discovery's `createdItemId` recorded. (2) A second inspection with two discoveries, one decided **MERGED** (into an existing item, with edited wording) and one left at the default **REJECTED** → confirm → version bumped exactly once (2→3... in that run's case 1→2) for the single finish despite two discoveries, the merged item's wording changed and no third item was added, the rejected discovery recorded `decision:'REJECTED'` with zero checklist impact. ## Week Overload view + load-aware flexible scheduling
Josh's goal: catch the specific failure mode where pushing tasks off a busy day (e.g. a full Tuesday) accidentally piles them all onto whatever day comes right after it, instead of spreading across whatever's actually free later in the week.

**Confirmed before starting, as asked:** the fixed-vs-flexible due date work (`dueType`, `dueDate`, `plannedDate`) was already in place, and — more importantly — `computeWeekSchedule()`/`buildCapacityForecast()` (`js/data.js`) already project a full 5-business-day-forward window, not just "today." This was **not** the bigger restructuring lift Josh flagged as a possibility; it was a direct amendment to an existing multi-day function plus a UI addition on top of it, so I went ahead and built both pieces without pausing.

**1. The scheduler amendment** — `computeWeekSchedule()`'s flexible-item placement loop was first-fit (earliest day in the window with any room at all). That's exactly what produces the reported bug: once a day fills, every subsequent flexible item takes the very next day in sequence, piling up there regardless of how empty days further out are. Changed to least-loaded-day-in-window: each flexible item (still processed earliest-deadline-first, so the item with the least slack still gets first pick) now scans every day *before* its due date for the one with the lowest currently-committed load that still has room, and only falls back to the due-date day itself if nothing earlier fits (forcing onto it as a last resort if even that's full — due date stays a hard deadline). Ties go to the earlier day, so front-loading is still the tiebreaker, just not the primary rule anymore. This is the single function both the daily Suggested Plan and the capacity forecast already read from, and it fully recomputes from scratch on every render — so a flexible item that gets missed and reshuffles into the pool the next day is handled by the exact same loop with no separate code path, as confirmed in testing (details below).

**2. Week Overload Check** — a new compact strip on the Brief tab, directly above the existing "Capacity — Next 5 Business Days" section (same data, `buildCapacityForecast()`, no second source of truth). Five small cells, one per day, each a day label + a thin colored bar (committed/budget) + the `used/budget` minutes. Tapping a cell expands that day's actual task list inline right below the strip; tapping the same cell again collapses it. Not a new tab, not a calendar — just this one glance-and-drill-in widget attached to the Brief view.

**Judgment calls to review:**
- **The "tight" (yellow) threshold is new, not reused** — there's no pre-existing three-tier capacity indicator anywhere in this app to copy; the existing Capacity section is strictly binary (green "done" stamp if it fits, red "overdue" stamp if it doesn't). Picked **80% of the daily budget** as the fits/tight boundary (`pct>=0.8`) and `used>budget` as the over boundary — both colors pulled from the existing `--stamp-green`/`--stamp-amber`/`--stamp-red` tokens already used elsewhere, just applied to a new middle tier. Easy to retune the single `0.8` constant in `weekOverloadStrip()` (`js/render.js`) if a different split feels better in practice.
- **The strip shows the rolling 5-business-day window, not a literal Monday-to-Sunday calendar block** — same window `computeWeekSchedule()`/the existing Capacity section already use (today + the next 4 business days, Mon-Fri only), labeled with each day's real weekday abbreviation. This app has no weekend capacity budget concept at all (`businessDaysForward()` skips Saturday/Sunday entirely), so a fixed Mon-Sun grid would show two dead cells every week and, depending what day it is, could include already-elapsed earlier-this-week days with nothing meaningful to report — neither helps the actual goal of seeing what's coming. If a literal calendar-week view turns out to be wanted after trying this, that's a bigger, separate UI decision, not a drop-in tweak.

Verified in a headless browser: (1) a scenario with today near-full and the next day completely full, plus 3 equal-size flexible items all due on the last day in the window — all 3 spread across the two emptier days instead of piling onto a single one (the old bug), and none were forced onto the due date itself since earlier days had room. (2) A reshuffle scenario: 2 flexible items placed on the two emptiest days, then a large fixed item added to the first day and the schedule recomputed fresh — both flexible items correctly relocated off the now-loaded day, confirming no special "reshuffle" code path is needed since this is pure derived recomputation. (3) The week strip renders 5 cells with correct weekday labels and correct fits/tight/over colors at the exact thresholds above, and tapping a cell shows that day's task list inline, tapping again collapses it.

## "What's booked" preview while picking a due date
Josh's ask: when moving a deficiency (or setting one for the first time), see what else is already booked on a candidate date before committing to it, so an overload isn't discovered after the fact.

Added a shared `bookingsForDate(dueDate, excludeId)` (`js/data.js`) — the same single source of truth as the Week Overload strip: if the picked date falls inside the existing 5-business-day computed window, it reads the *actual* scheduled day from `computeWeekSchedule()` (so a flexible item that the scheduler moved onto that date shows up even though its own `dueDate` field says something later); otherwise it falls back to a plain `dueDate` match, since the model doesn't compute placement that far out anyway. `excludeId` leaves out the item currently being moved/created so it never counts against its own candidate date. The existing save-time overbook warning (`joshBookingCount`) now just calls this same function instead of duplicating the filter.

Wired a live preview — description + estimate for every other Josh-owned item already on that date, plus an `N items · used/budget m` summary colored with the exact same fits(green)/tight(amber)/over(red) thresholds the Week Overload strip uses (80% of budget) — into all three places a due date gets picked or changed for a deficiency: the Add Deficiency modal, the Edit Deficiency modal (pre-filled immediately on open if the item already has a date), and the quick-date-picker on list rows in the Deficiencies → No Date tab. Updates live on every date keystroke/pick, with no threshold gate (even "1 other item, 60m" is worth seeing) — separate from, and in addition to, the existing >=2-items Save-time confirmation gate, which still blocks an accidental save. Only shown for Josh-owned items, matching the existing overbook check's scope — a Trade or Unassigned item's date doesn't compete for Josh's own time budget, so there's nothing to preview.

Verified in a headless browser: the Add modal's preview shows the correct item count/minutes/descriptions and the correct amber "tight" color for a date at 420/480 (87.5%), clears when switching the owner away from Josh, and the Edit modal's preview is pre-filled for an item that already has a date, updates live when a different date is picked (showing "0 items" on an empty day), and correctly excludes the item being edited from its own count — confirmed by editing one of two items already on a date and seeing the preview drop to "1 item," not "2."

## Manual bump/push for over-capacity days
Josh's goal: when he moves a task onto a day that's already at or over capacity, be able to push other items on that day forward himself — one at a time, confirmed each step — rather than it happening silently, or not at all.

**Confirmed before starting, as asked:** due dates were already editable on both fixed and flexible tasks everywhere a date gets set (Edit Deficiency, the quick-date-picker) — there was never a data-model restriction blocking it, so no adjustment was needed there. Built straight into the existing capacity engine (`computeWeekSchedule()`/`buildCapacityForecast()`) — no second capacity calculation.

**1. Fixed-deadline move confirmation.** Editing an *existing* due date on a fixed-type item (Edit Deficiency modal only — setting a date for the first time on an undated item isn't "moving" anything yet, so this doesn't fire there) now shows "This is marked as a fixed deadline — tap Save Changes again to move it anyway" before applying, the same repeated-tap-to-confirm pattern the existing overbook warning already uses. Applied this to the pre-existing Capacity section's "Push" button too, for consistency — previously that pushed a fixed item's due date with no confirmation at all; now it asks first, same as everywhere else a fixed deadline moves.

**2/3. The push cascade.** After any manual due-date save (Add, Edit, or the quick-date-picker) lands a Josh-owned fixed item on a day that's now at or over capacity, a new modal (`openCapacityCascadeModal()`) opens automatically showing every other item on that day — fixed and flexible both — each with a "Push to next business day" button. Pushing a **fixed** item moves its real `dueDate` forward one business day (same mechanism the Capacity section's button already used) and requires the same fixed-deadline confirm. Pushing a **flexible** item is different under the hood: flexible items have no separate "scheduled day" field (`computeWeekSchedule()` picks one fresh every render), so there's nothing to bump — instead it's *pinned* to the target day via `plannedDate`, the same "I'll actually do this Thursday" field Josh's own deferred-item scheduling already uses. `computeWeekSchedule()` now honors a valid pin ahead of its normal least-loaded auto-placement, and the pin gets invalidated automatically the same way `plannedDate` always has (its own due date changing clears it). A pinned flexible item shows "📌 pinned here" with an Unpin link to release it back to auto-placement.

After a push, the same day's cascade re-opens showing the updated list (one fewer item); if that push made the *next* day go over capacity too, a toast says so — it is never opened automatically, only offered, so every step stays a deliberate click as asked, never a silent chain reaction.

**4. Flexible push boundary.** Pushing a flexible item to a day past its own `dueDate` shows "Pushing '...' would move it past its own due date of ... — push anyway?" before applying (a confirm, not a hard block, matching the lightweight-guard spirit of the fixed-deadline check) — so a push can't silently blow a flexible item's real deadline.

**Judgment call — a literal view for this tool, not the forecast's.** `buildCapacityForecast()`'s `fits` list already *excludes* a fixed item from a day's count the moment the forecast's own forward-looking sort (smallest-estimate-first, so a single oversized item doesn't get to permanently crowd out everything else) decides something else should have that slot instead — correct for that forecast's own purpose, but wrong for a tool whose entire point is "what's literally sitting on this day so I can rebalance it": a fixed item Josh just explicitly dated to today needs to show up today regardless of how the forecast's sort would otherwise treat it. Added `literalDayBookings(day)` (`js/data.js`) for this feature specifically — literal `dueDate` match for fixed items (no cascade exclusion) plus the live computed placement for flexible items — used by both the cascade modal and the over-capacity trigger check. The earlier "what's booked" preview (previous section above) still uses the forecast-aware `bookingsForDate()`, unchanged; reconciling the two views more deeply was out of scope here and is flagged as a known, documented edge case below rather than something attempted today.

**Known edge case, for review:** because the auto-scheduler's own internal load bookkeeping (used to decide where a *flexible* item lands) is forecast-aware (cascade-exclusion) while this tool's view of "what's on a day" is literal, the two can disagree in one unusual situation — a single fixed item bigger than the entire daily budget by itself. In that specific case the auto-scheduler can treat that day as if it still had lots of spare room (since its own bookkeeping already "moved" the oversized item out of the way internally) and place a flexible item there, even though the literal view correctly shows that day as overloaded. Confirmed this directly with a headless browser rather than just reasoning about it. In Josh's realistic day-to-day numbers (task estimates well under a full 8-hour budget) this shouldn't come up — flagging it rather than rebuilding `computeWeekSchedule()`'s internal accounting to match, since that risks destabilizing the already-shipped auto-placement logic for a scenario that's unlikely to occur in practice.

Verified in a headless browser: the fixed-deadline confirm blocks a first Save click and applies on the second (and not at all when setting a first-time date, or when editing a flexible item's date); moving a fixed item onto an already-over-capacity day (a single 500m item on a 480m budget, confirmed as a genuinely over-capacity day first) opens the cascade modal showing every item literally dated there; pushing a fixed item shows a confirm and declining leaves its date untouched while accepting bumps it forward and the modal re-shows the updated day; pushing a flexible item with slack applies immediately via a `plannedDate` pin with no confirm, and `computeWeekSchedule()` correctly moves it to the new day on the next render; pushing a flexible item with zero slack (due today) correctly shows the past-the-deadline confirm before applying; the quick-date-picker correctly triggers the cascade offer the same as Add/Edit; and the pre-existing Capacity section Push button now shows the same fixed-deadline confirm.

## Access code
